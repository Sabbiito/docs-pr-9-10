## 1. Вступ

### 1.1. Призначення документа

Цей документ описує технічну специфікацію системи Connect Four: архітектуру, функціональні та нефункціональні вимоги, модель даних, зовнішні інтерфейси та обмеження реалізації. Документ призначений для розробників, які супроводжують чи розширюють проєкт, а також для технічної оцінки відповідності реалізації поставленим вимогам.

### 1.2. Область застосування

Специфікація охоплює дві частини системи:

- **клієнтський застосунок** — React SPA, що реалізує повний цикл гри «4 в ряд» для двох гравців на одному пристрої, з локальним збереженням стану в браузері;
- **опційний серверний компонент** — мінімальний REST API для синхронізації статистики завершених ігрових сесій на сервер і перегляду загального лідерборду.

Серверний компонент є доповненням, а не заміною клієнтської логіки: застосунок повністю функціональний без будь-якого мережевого з'єднання із сервером.

### 1.3. Терміни та скорочення

| Термін | Визначення |
|---|---|
| Сесія (session) | Серія матчів з однаковими налаштуваннями (розмір дошки, умова перемоги), що накопичує сукупну статистику |
| Матч (game) | Одна завершена гра в межах сесії — до перемоги одного з гравців або нічиї |
| Синхронізація | Явна дія користувача з передачі підсумкової статистики сесії на сервер |
| Лідерборд | Серверний агрегований список синхронізованих сесій, відсортований за кількістю перемог |
| Consent-aware сховище | Адаптер localStorage, що фізично блокує запис даних для категорій, на які користувач не надав згоду |

## 2. Загальний опис системи

### 2.1. Контекст системи

Система складається з двох незалежно розгортуваних частин, що взаємодіють через один HTTP-контракт (REST API), задокументований в OpenAPI-специфікації `server/openapi.yaml`:

```
┌─────────────────────────────┐         ┌──────────────────────────────┐
│   Клієнт (браузер)           │  HTTPS  │   Сервер (Node.js/Express)    │
│   React SPA                  │────────▶│   REST API                     │
│   ├─ Ігрова логіка            │  (опц.) │   ├─ POST /leaderboard/sync    │
│   ├─ localStorage (стан)      │         │   ├─ GET  /leaderboard         │
│   └─ GDPR-згода               │         │   └─ In-memory сховище         │
└─────────────────────────────┘         └──────────────────────────────┘
```

Мережева взаємодія — опційна й одностороння: клієнт ініціює запити до сервера, сервер ніколи не звертається до клієнта самостійно.

### 2.2. Функції системи

Система реалізує чотири групи функцій.

Перша — власне ігровий процес: створення сесії з обраними налаштуваннями, здійснення ходів по черзі, автоматична перевірка умови перемоги в чотирьох напрямках (горизонталь, вертикаль, дві діагоналі), визначення нічиї, підрахунок статистики в межах сесії.

Друга — управління сесіями: перегляд списку всіх локальних сесій, перегляд статистики конкретної сесії, видалення однієї сесії або очищення всієї історії.

Третя — забезпечення відповідності GDPR: показ банера згоди при першому відвідуванні з можливістю прийняти все, відхилити все або налаштувати категорії окремо; технічне блокування запису в localStorage для категорій без згоди; можливість відкликати згоду в будь-який момент через сторінку «Конфіденційність».

Четверта — опційна серверна синхронізація: передача підсумкової статистики завершеної сесії на сервер за явним вибором користувача та перегляд загального лідерборду серед усіх синхронізованих сесій.

### 2.3. Характеристики користувачів

Цільовий користувач — будь-яка особа, що хоче зіграти в «4 в ряд» з іншою особою на одному пристрої (браузер настільного або мобільного пристрою), без потреби створювати обліковий запис чи встановлювати окремий застосунок. Спеціальних технічних знань не потрібно.

## 3. Функціональні вимоги

Нижче наведено функціональні вимоги у форматі «система повинна». Кожна вимога має ідентифікатор для трасування до реалізації.

**FR-1.** Система повинна дозволяти користувачу створити нову ігрову сесію з обраними налаштуваннями: імена двох гравців, розмір дошки (6×7, 7×8 або 8×9), умова перемоги (кількість фішок у ряд), колір дошки. Реалізовано в `StartPage.jsx` та `settingsStore.js`.

**FR-2.** Система повинна дозволяти гравцям по черзі здійснювати ходи, кидаючи фішку в обрану колонку; фішка займає найнижчу вільну клітинку цієї колонки. Реалізовано в `useGameBoard.js`, `GameBoard.jsx`.

**FR-3.** Система повинна автоматично перевіряти після кожного ходу, чи утворилася переможна лінія заданої довжини в одному з чотирьох напрямків, і завершувати матч з визначенням переможця. Реалізовано в `useWinDetection.js`.

**FR-4.** Система повинна визначати нічию, коли дошка повністю заповнена і жодна лінія перемоги не утворена. Реалізовано в `useGameLogic.js`.

**FR-5.** Система повинна накопичувати статистику (перемоги кожного гравця, нічиї, загальна кількість матчів) у межах поточної сесії та зберігати її після кожного завершеного матчу. Реалізовано в `sessionStore.js`.

**FR-6.** Система повинна відображати список усіх локально збережених сесій з можливістю переглянути статистику кожної, видалити окрему сесію або очистити всю історію. Реалізовано в `SessionsPage.jsx`.

**FR-7.** Система повинна при першому відвідуванні показати банер згоди на використання localStorage з трьома варіантами дії: прийняти все, відхилити все, налаштувати категорії окремо («Налаштування гри», «Історія та статистика»). Реалізовано в `CookieConsentBanner.jsx`, `consentStore.js`.

**FR-8.** Система повинна фізично унеможливлювати запис даних у localStorage для категорій, на які згоду не надано (а не лише приховувати відповідний функціонал в інтерфейсі). Реалізовано в `consentAwareStorage.js`.

**FR-9.** Система повинна дозволяти користувачу в будь-який момент переглянути поточний статус згоди та відкликати її через сторінку «Конфіденційність» (`/privacy`). Реалізовано в `PrivacyPage.jsx`, метод `resetConsent`.

**FR-10.** Система повинна за явним вибором користувача передавати підсумкову статистику завершеної сесії на сервер через `POST /api/v1/leaderboard/sync`. Повторна синхронізація тієї самої сесії повинна оновлювати наявний серверний запис, а не створювати дублікат.

**FR-11.** Система повинна надавати публічний доступ на читання до агрегованого лідерборду всіх синхронізованих сесій через `GET /api/v1/leaderboard`, відсортованого за сумарною кількістю перемог обох гравців.

**FR-12.** Сервер повинен валідувати вхідні дані запиту синхронізації (обов'язкові поля, типи, узгодженість `totalGames` із сумою решти лічильників) і повертати код 400 з деталізованим описом помилки при недійсних даних.

## 4. Нефункціональні вимоги

**Продуктивність.** Перевірка умови перемоги (FR-3) реалізована з обчислювальною складністю O(k), де k — задана довжина переможної лінії, а не O(n×m) від повного розміру дошки, оскільки алгоритм аналізує лише клітинку останнього ходу в чотирьох напрямках. Це забезпечує миттєвий відгук інтерфейсу незалежно від обраного розміру дошки.

**Портативність.** Клієнтська частина не має залежностей від конкретної операційної системи чи пристрою — вимагається лише сучасний веббраузер з підтримкою ES2018+ та localStorage.

**Доступність без мережі.** Основний ігровий функціонал (FR-1–FR-9) повністю доступний офлайн після першого завантаження сторінки; мережеве з'єднання потрібне лише для опційної синхронізації (FR-10, FR-11).

**Безпека.** Серверна частина застосовує стандартні захисні HTTP-заголовки (пакет `helmet`), обмеження частоти запитів (100 запитів / 15 хвилин з одного IP-джерела) та валідацію розміру тіла запиту (ліміт 100 KB) для протидії зловживанню публічним ендпоінтом.

**Конфіденційність.** Обробка даних відповідає вимогам GDPR (див. окремий документ `PRIVACY_POLICY.md`): мінімізація обсягу даних, явна згода перед збереженням, право на видалення та відкликання згоди технічно реалізовані, а не лише задекларовані.

**Ліцензійна чистота.** Усі 1240 прямих і транзитивних залежностей клієнтської частини перевірені інструментом `license-checker` на відсутність конфліктів із сильним copyleft (GPL/AGPL/LGPL) — див. `LICENSE-REPORT.md`.

**Тестованість.** Ігрова логіка, GDPR consent-механізм та обидва серверні ендпоінти покриті автоматизованими тестами (16 клієнтських тестів на Jest/RTL, 7 серверних тестів на вбудованому test runner Node.js).

**Персистентність (обмеження).** Серверне сховище лідерборду реалізоване в оперативній пам'яті процесу (in-memory) і навмисно не використовує зовнішню БД — це свідоме спрощення для навчального проєкту, задокументоване в коді (`server/src/data/leaderboardStore.js`). Дані лідерборду не переживають перезапуск серверного процесу; клієнтські дані в localStorage цього обмеження не мають.

## 5. Архітектура та дизайн

### 5.1. Архітектура клієнта

Клієнт побудований за компонентною архітектурою React з чітким поділом відповідальності на чотири шари.

Шар **компонентів представлення** (`src/components/`) відповідає виключно за візуалізацію та не містить бізнес-логіки; поділений на `common` (перевикористовувані елементи — кнопки, картки), `game` (елементи, специфічні для ігрового процесу) та `modals`.

Шар **хуків** (`src/hooks/`) інкапсулює обчислювальну логіку, відокремлену від відображення: `useGameBoard` керує станом матриці дошки, `useWinDetection` — алгоритмом перевірки перемоги, `useGameLogic` — оркеструє обидва попередні разом із чергою ходів, `useGameStats` — підрахунком статистики.

Шар **глобального стану** (`src/store/`) на основі Zustand містить чотири незалежні стори: `gameStore` (легкий знімок поточного ходу, без персистентності), `settingsStore` та `sessionStore` (персистентні, через consent-aware сховище), `consentStore` (стан GDPR-згоди).

Шар **сторінок і маршрутизації** (`src/pages/`, `src/router/`) на основі React Router v7 зв'язує решту шарів у цілісний користувацький потік.

### 5.2. Архітектура сервера

Сервер побудований за класичною тришаровою структурою Express-застосунку: шар **маршрутів** (`src/routes/leaderboard.js`) обробляє HTTP-запити та виконує валідацію вхідних даних; шар **даних** (`src/data/leaderboardStore.js`) інкапсулює сховище за інтерфейсом, незалежним від конкретної реалізації (заміна in-memory на реальну БД не вимагає зміни контракту маршрутів); конфігурація застосунку (`src/app.js`) окремо від точки запуску (`src/index.js`) дозволяє тестувати HTTP-рівень без відкриття мережевого порту (використано в тестах через `supertest`).

### 5.3. Модель даних

**Клієнтська модель `GameSession`** (`src/store/sessionStore.js`):

```
GameSession {
  id: string              // "session_<timestamp>"
  settings: object         // знімок налаштувань на момент створення
  stats: {
    player1Wins: number
    player2Wins: number
    draws: number
    totalGames: number
  }
  createdAt: string        // ISO 8601
  lastPlayedAt: string     // ISO 8601
}
```

**Серверна модель `LeaderboardEntry`** (`server/src/data/leaderboardStore.js`) — свідомо спроєктована як підмножина полів `GameSession`, необхідна для публічного лідерборду, без внутрішніх службових полів клієнта:

```
LeaderboardEntry {
  sessionId: string
  playerOneName: string
  playerTwoName: string
  stats: { player1Wins, player2Wins, draws, totalGames }
  syncedAt: string          // ISO 8601, момент синхронізації
}
```

### 5.4. Зовнішні інтерфейси

Повний контракт REST API формально описаний у файлі `server/openapi.yaml` (специфікація OpenAPI 3.0.3) і доступний інтерактивно через Swagger UI за адресою `/api-docs` під час роботи сервера. Postman-колекція з готовими прикладами запитів і автоматизованими перевірками відповіді знаходиться в `server/postman/Connect-Four-Leaderboard-API.postman_collection.json`.

| Метод | Шлях | Призначення |
|---|---|---|
| `POST` | `/api/v1/leaderboard/sync` | Синхронізувати статистику однієї сесії (upsert за `sessionId`) |
| `GET` | `/api/v1/leaderboard` | Отримати повний лідерборд, відсортований за перемогами |
| `GET` | `/api/v1/health` | Перевірка стану сервера |

## 6. Обмеження та припущення

Система розрахована на гру двох осіб на одному фізичному пристрої (одна клавіатура/екран, по черзі); підтримка гри двох гравців з різних пристроїв через мережу не входить до області застосування цієї версії.

Серверний компонент є прототипом опційної функції соціального порівняння результатів і не призначений для промислового навантаження: відсутні авторизація, персистентна БД та горизонтальне масштабування.

Припускається, що користувач має сучасний браузер з увімкненим JavaScript та підтримкою localStorage; застосунок не надає деградованої (no-JS) версії функціоналу.
